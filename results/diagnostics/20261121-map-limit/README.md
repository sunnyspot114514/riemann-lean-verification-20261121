## 可复现的故障

对第一个失败模块 `Development.AutomorphicArithmetic.CharacterBoxes.ShapeWin`，保留原始命令中的官方 Lean、输入源码、`-j1`、`--tstack=400000`、`--setup` 和原有 LEAN_PATH，仅移除 `-o / -i / -c` 输出参数，避免与正在运行的 Lake 写入同一组产物。加入 strace 记录失败系统调用，并只读采样 /proc 中的映射数量。

该次诊断在约 10.19 秒后以退出码 1 结束，复现了原始日志中的同一条错误。报错涉及的 GoodParameterFirstSpace.olean 存在，大小为 368,952 字节。

采样的映射数量达到 65,532，接近并触及当前 65,530 的内核阈值。strace 连续记录到文件映射与匿名内存映射失败：

```text
mmap(..., 368952, ..., MAP_PRIVATE|MAP_FIXED_NOREPLACE, 9, 0) = -1 ENOMEM
mmap(NULL, 372736, ..., MAP_PRIVATE|MAP_ANONYMOUS, -1, 0) = -1 ENOMEM
read(9, NULL, 368952) = -1 EFAULT
```

官方 [Lean v4.33.1 的读取实现](https://github.com/leanprover/lean4/blob/v4.33.1/src/library/module.cpp#L454-L565) 在 mmap 未成功时，回退到 malloc + read；此路径没有先检查 malloc 是否返回空指针。这里的空指针读取因而被包装成没有 errno 的通用 `failed to read file` 报错。

**已经确认至少这个模块的失败由进程映射资源耗尽触发。** 其余 11 处错误具有相同的通用报错形态，但尚未逐一做系统调用复现，不能声称每一处都已单独诊断。所有 12 个错误涉及的 .olean 文件在检查时均存在，详细元数据保存在 evidence.json。

这项诊断未出现数学类型检查失败的证据，也没有验证完整证明。不能据此宣布黎曼猜想已获验证。

## 后续处理

优先通过云平台支持的宿主机配置，把 `vm.max_map_count` 提高到例如 `1048576`，并在容器内重新读取该值确认生效。此前在当前容器内执行普通 sysctl 修改被权限拒绝，容器内 root 并不具备更改该宿主机参数的权限。

增加磁盘容量到 2 TB 不会改变这项上限；单纯降低并发也不会提高单进程的映射数量限制。当前没有发现官方 Lean 4.33.1 的运行时开关可以关闭这里的逐文件 mmap。glibc 的 malloc 参数不控制 Lean 的显式文件 mmap，不能作为可靠修复。

本次不清空成功模块，不在同一构建目录启动第二个 Lake。当前全量任务仍可为其他模块积累有效的编译产物。解决宿主机限制后，可以正常增量重跑 Main；Lake 会根据 trace/hash 复用有效产物，原始失败日志和退出码必须保留。

最终仍要求四个关卡全部成功：
1. build-main
2. axioms
3. validate-axioms
4. fresh-replay

逐模块构建和完成后删除 .setup.json 可以控制临时磁盘占用，但最终 Main 导入与完整重放仍需要加载完整依赖闭包。宿主机参数修复也不保证后续阶段不会遇到其他资源或证明问题。
